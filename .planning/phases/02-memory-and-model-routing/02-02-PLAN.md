**Step 3: Create `~/.openclaw/src/router/classifier.ts`** -- Task classification:

- `loadRouterConfig(configPath?)`: Read `~/.openclaw/config/model-routing.yaml` using yaml library. Parse and return as RouterConfig. Cache the result.
- `classifyTask(task, context?)`: Takes a task description string and optional context string. Returns `TaskClass`.
  1. Lowercase the task + context.
  2. For each tier in config classification rules (check in order: opus first for client-facing priority, then sonnet, then ollama), test if any keyword appears in the text.
  3. If a match is found, return that tier with the matched keywords.
  4. Default to "haiku" for unmatched tasks (standard tier per user decision).
  5. Per user decision: "Default to the most capable tier likely to succeed first try" -- the classifier should not aggressively downgrade. When in doubt, use haiku (not ollama).
- Export `CLASSIFICATION_RULES` as a readable mapping for debugging.

**Step 4: Create `~/.openclaw/src/router/router.ts`** -- Model dispatch with fallback:

- `healthCheck(tier)`: For Ollama: `GET http://127.0.0.1:11434/api/tags` with a timeout of `ollama_timeout_ms` from config. Return true if response received within timeout. For Claude tiers: always return true (Anthropic SDK handles retries).
- `callTier(tier, messages, systemPrompt, config)`: Internal function.
  - For "ollama": Use `ollama.chat({ model: config.tiers.ollama.model, messages: [{ role: "system", content: systemPrompt }, ...messages] })`. Extract content from `response.message.content`. Get token counts from `response.prompt_eval_count` and `response.eval_count`. Cost is 0.
  - For Claude tiers ("haiku", "sonnet", "opus"): Use `anthropic.messages.create({ model: config.tiers[tier].model, max_tokens: config.tiers[tier].max_tokens, system: systemPrompt, messages })`. Handle prompt caching (delegate to prompt-cache module). Extract content from `response.content[0].text`. Calculate cost from `response.usage` fields using config cost rates. Track cache_read_input_tokens and cache_creation_input_tokens.
  - Wrap in try/catch. On error, throw with descriptive message including tier and error.
- `routeAndCall(task, messages, systemPrompt, sessionId)`: Main entry point.
  1. Classify the task via `classifyTask(task)`.
  2. Get the tier index in `fallback_order`.
  3. For each tier from the classified tier onward:
     a. If Ollama, check health first. Skip if unhealthy.
     b. Call `callTier()`.
     c. On success: log the call (structured JSON to stderr), return ModelCallResult.
     d. On failure: log the error (structured JSON), continue to next tier.
  4. If a fallback occurred (actual tier != classified tier), include `fallback_from` in the result and log a WARN-level event: `{ level: "WARN", component: "model-router", action: "FALLBACK", original_tier, actual_tier, reason }`.
  5. If ALL tiers fail, throw an error: "All model tiers exhausted -- no response possible".
  6. Record timing (measure latency_ms from start to response).

**Step 1: Create `~/.openclaw/src/router/prompt-cache.ts`** -- Prompt caching for Claude API calls:

- `buildCachedSystemPrompt(basePrompt, memoryContent?)`: Builds a system prompt optimized for caching.
  1. Start with the static base prompt (personality, rules, safety directives) -- this MUST come first for cache stability.
  2. Append MEMORY.md content (from `loadMemory()` if memoryContent not provided).
  3. The combined static content forms the cacheable prefix.
  4. Dynamic content (current time, session context) goes AFTER the cache breakpoint -- never at the start.
  5. Return the assembled system prompt string.
  6. Per anti-pattern guidance: if the system prompt is below minimum token thresholds (1024 for Haiku/Sonnet, 4096 for Opus), pad with MEMORY.md content or structured context to exceed the minimum. Log a warning if the prompt is still too short for the tier.
- `getCacheConfig(tier)`: Returns the Anthropic API cache_control configuration for the given tier.
  - Returns `{ type: "ephemeral" }` for automatic caching (simplest approach per research).
  - Only enabled if `config.cache.enabled` is true and the system prompt exceeds the tier's minimum token count.
- `trackCachePerformance(usage, tier)`: Log cache metrics from the API response:
  - `cache_read_input_tokens`: tokens read from cache (cheap -- 10% of base price)
  - `cache_creation_input_tokens`: tokens written to cache (expensive -- 125% of base price)
  - `input_tokens`: uncached input tokens
  - Compute and log the cache hit ratio: `cache_read / (cache_read + cache_creation + uncached)`.
  - Structured JSON log: `{ level: "INFO", component: "prompt-cache", tier, cache_read_tokens, cache_creation_tokens, uncached_tokens, hit_ratio }`.

**Step 2: Create `~/.openclaw/src/router/cost-tracker-integration.ts`** -- Wire router to Phase 1 cost tracker and Phase 2 daily log:

- `recordModelUsage(result: ModelCallResult, sessionId: string)`: Takes the result from `routeAndCall()` and:
  1. Call `recordUsage()` from `~/.openclaw/src/cost/tracker.ts` with the mapped UsageRecord:
     ```
     { timestamp: new Date().toISOString(), session_id: sessionId, model: result.model,
       input_tokens: result.input_tokens, output_tokens: result.output_tokens,
       cost_usd: result.cost_usd, tool_calls: 0 }
     ```
  2. This ensures the Phase 1 circuit breaker ($50/month cap, session limits) remains enforced for all model calls routed through the router.
- `getDailyCostSummary(dbPath?)`: Query the cost tracker database for today's usage grouped by model. Return a formatted string like:
  ```
  Today: $0.42 total -- Haiku $0.28 (1.2M tok), Sonnet $0.12 (40K tok), Opus $0.02 (2K tok), Ollama $0.00 (500K tok)
  ```
  Per user's specific idea: "Cost summaries should look like: 'Today: $0.42 total -- Haiku $0.28, Sonnet $0.12, Opus $0.02, Ollama $0.00'"
- `logDailyCostSummary(dbPath?)`: Calls `getDailyCostSummary()` and writes it to the daily log via `logEntry({ type: "cost", summary: costString })`. Intended to be called at end of day or on demand. Per user decision: "Daily cost summary: track tokens and costs per model per day, surface in daily log and weekly summaries."
