Install Notion SDK: `cd ~/.openclaw && npm install @notionhq/client`

Create `src/calendar/client.ts`:
- `createCalendarClient(auth?: OAuth2Client): calendar_v3.Calendar` -- creates `google.calendar({ version: 'v3', auth })`. If no auth provided, calls `getOAuth2Client()` from gmail/client.ts (shared OAuth2 -- both Gmail and Calendar use the same OAuth2 client since scopes were requested together in 03-02).
- `insertCalendarEvent(event: ExtractedCalendarEvent, auth?: OAuth2Client): Promise<string>` -- calls `calendar.events.insert()` with calendarId 'primary'. Parses the ExtractedCalendarEvent into Google Calendar event format: `{ summary: event.title, start: { dateTime: ISO8601 }, end: { dateTime: ISO8601 }, location: event.location, description: event.description }`. For end time: if endTime provided use it, else if duration provided compute from startTime + duration, else default to startTime + 1 hour. Returns the created event's htmlLink for confirmation. Log to stderr with `component: "calendar-client"`.

Create `src/calendar/awareness.ts`:
- `isOperatorBusy(auth?: OAuth2Client): Promise<boolean>` -- uses `calendar.freebusy.query()` with timeMin = now, timeMax = now + 5 minutes, items = [{ id: 'primary' }]. Returns true if busy array is non-empty. Per research code example.
- `getNextFreeSlot(auth?: OAuth2Client, lookAheadHours?: number): Promise<Date | null>` -- uses `calendar.events.list()` for the next N hours (default 4), finds the first gap of at least 15 minutes. Returns the start of that gap, or null if fully booked.
- `shouldDeferMessage(priority: 'urgent' | 'normal', auth?: OAuth2Client): Promise<boolean>` -- returns false for urgent messages (always send). For normal messages, returns true if `isOperatorBusy()` is true. This is the check before sending any non-urgent Telegram message.
- Follow structured JSON logging pattern to stderr with `component: "calendar-awareness"`.

Create `src/notion/types.ts`:
- `LogActionType` type: `'email-triage' | 'calendar-add' | 'hitl-approval' | 'hitl-rejection' | 'system' | 'error'`
- `LogEntry` interface: `{ action: string; type: LogActionType; status: 'completed' | 'pending' | 'failed'; source: string; timestamp: Date; metadata?: Record<string, string>; }`
- `NotionConfig` interface: `{ apiKey: string; actionLogDbId: string; notionVersion: string; }`

Create `src/notion/client.ts`:
- `createNotionClient(apiKey?: string): Client` -- creates `new Client({ auth: apiKey || process.env.NOTION_API_KEY, notionVersion: '2025-09-03' })`. Per research, use API version 2025-09-03 for data_source_id support.
- `getDataSourceId(databaseId: string, client?: Client): Promise<string>` -- calls `notion.databases.retrieve({ database_id: databaseId })`, returns `db.data_sources[0].data_source_id`. Cache the result in module scope after first call. Per research Pitfall 4, use data_source_id instead of database_id for page creation.
- Follow structured JSON logging pattern to stderr with `component: "notion-client"`.

Create `src/notion/action-log.ts`:
- `logAction(entry: LogEntry, client?: Client, dbId?: string): Promise<void>` -- creates a Notion page in the Action Log database. Uses `getDataSourceId()` for the parent. Properties: Action (title), Type (select), Status (select), Source (rich_text), Timestamp (date). If Notion API call fails, log error to stderr but do NOT throw -- action logging should never block the primary workflow. This is a fire-and-forget pattern.
- `logBatch(entries: LogEntry[], client?: Client, dbId?: string): Promise<void>` -- logs multiple entries sequentially (Notion API does not support batch page creation). Useful for logging all triage results at once.
- Default dbId: `process.env.NOTION_ACTION_LOG_DB_ID`.
