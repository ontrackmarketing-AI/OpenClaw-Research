**1. Create `~/.openclaw/src/task-rag/pre-task-recall.ts`:**

Imports:

**Type: `RecallResult`**
```typescript
export interface RecallResult {
  outcomes: OutcomePayload[];
  lessons: string;         // Formatted for injection into system prompt
  recall_count: number;
}
```

**Function: `loadRecallConfig(taskType: string): { limit: number; threshold: number }`**
- Load `~/.openclaw/config/task-rag.yaml`
- Return `recall_limit` and `recall_threshold` for the given task type
- Fall back to `{ limit: 3, threshold: 0.6 }` if config missing or task type not found

**Function: `recallForTask(taskType: string, currentContext: string, options?: { limit?: number; threshold?: number; qdrant?: QdrantClient; ollama?: Ollama }): Promise<RecallResult>`**
- Get collection name via `getCollectionName(taskType)`. If unknown task type, return empty RecallResult.
- Load recall config. Use options overrides if provided, otherwise config values.
- Embed `currentContext` via `embed()`
- Search the task-specific collection:
  ```typescript
  qdrant.search(collectionName, {
    vector: queryEmbedding,
    limit: limit * 2,  // Fetch extra for post-filter scoring
    score_threshold: threshold,
    with_payload: true,
    filter: {
      should: [
        { key: "status", match: { value: "confirmed" } },
        { key: "status", match: { value: "pending" } },
      ],
    },
  })
  ```
- Post-process: weight confirmed entries 2x by multiplying their score by 1.0 and pending entries by 0.5, then sort by adjusted score descending
- Take top `limit` results
- Extract OutcomePayload from each result's payload
- Format lessons via `formatLessons()`
- Return `{ outcomes, lessons, recall_count }`
- Structured JSON log: `{ component: "pre-task-recall", action: "RECALL_COMPLETE", task_type, results, top_score }`

**Function: `formatLessons(outcomes: OutcomePayload[], taskType: string): string`**
- If no outcomes, return `""`
- Build formatted string:
  ```
  ## Past ${taskType} Outcomes (${outcomes.length} relevant)
  - AVOID: ${error_type} when handling "${input_summary}" -- ${error_message}
  - CORRECTION: Operator changed output for "${input_summary}" -- ${operator_correction}
  - LEARNED: ${patterns_observed}
  - SUCCESS PATTERN: "${input_summary}" -> ${output_summary}
  ```
- Prioritize in this order: errors first, corrections second, patterns third, successes last
- Cap total output at 500 tokens (approximately 2000 chars). Truncate from the bottom (drop success patterns first).
- Export this function

**Function: `preExecutionHook(taskType: string, currentContext: string, baseSystemPrompt: string, options?: { qdrant?: QdrantClient; ollama?: Ollama }): Promise<string>`**
- Call `recallForTask(taskType, currentContext, options)`
- If `recall.lessons` is non-empty, append to system prompt as dynamic context:
  - Return `baseSystemPrompt + "\n\n--- Task History ---\n" + recall.lessons`
  - IMPORTANT: This goes in the `dynamicContext` position relative to prompt caching. The caller should pass the recall-enhanced prompt as the `dynamicContext` parameter to `buildCachedSystemPrompt()` (Pitfall 2 from research: recall goes AFTER the cache breakpoint, not within the cacheable prefix).
- If no lessons, return `baseSystemPrompt` unchanged
- For Ollama tier tasks: consider skipping recall entirely (classification tasks don't benefit). Add `skipOllama` option that defaults to true -- if the task was classified to Ollama tier, skip recall to save embedding cost.

**Type: `ClientKnowledgeEntry`**
```typescript
export interface ClientKnowledgeEntry {
  contact_id: string;          // Opaque CRM identifier (NOT raw email/phone)
  contact_name: string;
  knowledge_type: "interaction" | "preference" | "project" | "feedback" | "history";
  content: string;             // The knowledge itself
  source: string;              // "email-triage", "proposal-gen", "check-in", "todo", etc.
  timestamp: string;           // ISO 8601
}
```

**Function: `deterministicClientKnowledgeId(contactId: string, timestamp: string): number`**
- Hash input: `client-knowledge:${contactId}:${timestamp}`
- Same djb2 hash formula as outcome-indexer's deterministicOutcomeId
- Return `Math.abs(hash) % 2147483647 || 1`

**Function: `checkClientKnowledgeDuplicate(contactId: string, content: string, qdrant?: QdrantClient, ollama?: Ollama): Promise<boolean>`**
- Embed `content`
- Search client-knowledge collection with filter: `contact_id = contactId`, `limit: 1`, `score_threshold: 0.90` (slightly lower than outcome dedup because client knowledge is more varied)
- If match found above threshold, return `true` (is duplicate)
- Otherwise return `false`
- This prevents the "Acme Corp prefers email" being stored 5 times from different sources (Pitfall from research open question 4)

**Function: `indexClientKnowledge(entry: ClientKnowledgeEntry, options?: { qdrant?: QdrantClient; ollama?: Ollama }): Promise<{ indexed: boolean; reason?: string }>`**
- Check for duplicate via `checkClientKnowledgeDuplicate()`. If duplicate:
  - Find the existing point via search and update its `source` field to include the new source (e.g., "email-triage,proposal-gen")
  - Return `{ indexed: false, reason: "duplicate_updated_source" }`
- If not duplicate:
  - Embed the content
  - Generate deterministic point ID
  - Upsert into client-knowledge collection with payload: all ClientKnowledgeEntry fields + `status: "pending"`, `indexed_at: new Date().toISOString()`
  - Log: `{ type: "action", summary: "Client knowledge: indexed ${entry.knowledge_type} for ${entry.contact_name} from ${entry.source}" }`
  - Return `{ indexed: true }`

**Function: `queryClientKnowledge(options: { contactId?: string; query?: string; limit?: number; qdrant?: QdrantClient; ollama?: Ollama }): Promise<ClientKnowledgeEntry[]>`**
- If `query` is provided (semantic search -- "what do we know about [client]?"):
  - Embed the query
  - Build filter: if `contactId` also provided, add `contact_id` must-match
  - `qdrant.search()` with `score_threshold: 0.5`, `with_payload: true`
  - Return payloads as ClientKnowledgeEntry[]
- If only `contactId` provided (direct lookup):
  - `qdrant.scroll()` with `filter: { must: [{ key: "contact_id", match: { value: contactId } }] }`, `with_payload: true`, `limit: limit || 10`
  - Return payloads as ClientKnowledgeEntry[]
- If neither, return `[]`
- Always prefer passing `contactId` when querying for a specific person to avoid cross-client conflation (Pitfall 5 from research)
- Structured JSON log: `{ component: "client-knowledge", action: "QUERY", query_type: query ? "semantic" : "direct", contact_id, results }`

**Function: `buildClientKnowledgeFromOutcome(taskType: string, input: { summary: string; contactId?: string; contactName?: string }, result: { success: boolean; output: string }): string | null`**
- If no `contactId` or no `contactName`, return `null` (not client-related)
- Build knowledge string based on task type:
  - `email-triage`: `"Email interaction with ${contactName}: ${input.summary}. Result: ${result.output.slice(0, 200)}"`
  - `proposal-gen`: `"Proposal generated for ${contactName}: ${input.summary}. ${result.success ? 'Delivered' : 'Failed'}"`
  - `check-in`: `"Check-in context for ${contactName}: ${input.summary}"`
  - Default: `"${taskType} interaction with ${contactName}: ${input.summary}"`
- Return the knowledge string (caller wraps in ClientKnowledgeEntry)
- Export this function (used by postExecutionHook in outcome-indexer when contact info is present)
